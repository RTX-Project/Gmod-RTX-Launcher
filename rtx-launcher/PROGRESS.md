## СЛЕДУЮЩАЯ ЗАДАЧА (приоритет №1): Библиотека версий RTX Remix

### Цель
Заменить текущую простую страницу «Обновления RTX Remix» (две кнопки
«Проверить обновления» / «Скачать обновление») на полноценный экран в
стиле лаунчера **Playnite** (карточка игры + список библиотеки): слева
— прокручиваемый список версий (релизов)
RTX Remix, справа — карточка выбранной версии с баннером, кнопками
действия и двумя колонками (Детали / Описание).

### Референсы
Пользователь приложил два скриншота лаунчера **Playnite** (open-source
менеджер библиотеки игр, не GOG Galaxy — визуально похожи, но это
разные программы) (сами файлы
изображений не сохранены в репозитории — ниже их точное текстовое
описание, этого достаточно для реализации):

1. **Карточка игры** — полноширинный баннер-обложка сверху; поверх
   баннера слева — название крупным шрифтом; под названием — две кнопки
   в ряд: акцентная голубая **«Play»** и тёмная **«More»**. Ниже баннера
   — две колонки: слева **«Details»** (список пар ключ-значение,
   формат — просто подпись слева и значение справа/снизу), справа
   **«Description»** — заголовок и текст описания, под текстом —
   скриншот/картинка.
2. **Список библиотеки** — узкая вертикальная панель со списком
   элементов: у каждого — маленькая круглая иконка слева и название
   справа; выбранный пункт выделен акцентным цветом текста и тонкой
   вертикальной полосой слева (у нас это уже есть как приём в
   `Theme::DrawNavItem` — переиспользовать тот же визуальный язык).

### Точные требования к реализации

**A. Список версий (левая под-панель внутри страницы «Обновления», ширина ~260px)**
- Получать список релизов через `GET https://api.github.com/repos/{owner}/{repo}/releases`
  (обычный список, НЕ `/releases/latest`) — до 15-20 штук.
- Добавить в `RtxRemixUpdater.h` метод
  `std::vector<RtxReleaseInfo> listReleases(int count, LogFn log)`,
  переиспользующий существующие `HttpClient::getText` и `JsonValue`.
  `JsonValue::parse` уже умеет разбирать JSON-массив верхнего уровня
  без изменений (тип определяется автоматически по первому символу
  ответа) — менять `JsonValue.h` не нужно.
- В `RtxReleaseInfo` добавить поля: `htmlUrl` (из `html_url`),
  `publishedAt` (из `published_at`, обрезать до `YYYY-MM-DD`), `body`
  (из `body` — текст описания релиза).
- Каждая строка списка — owner-draw пункт (аналог `MakeNavItem` +
  `Theme::DrawNavItem`), показывает: имя релиза (`name`, если пусто —
  `tag_name`) и дату публикации. Пункт, совпадающий с версией из
  `.rtx_remix_version.txt` рабочей папки, помечен как «✓ установлено»
  (доп. текст или иконка).
- Прокрутка списка не обязательна в первой итерации, если высоты
  страницы хватает на 15-20 пунктов; если нет — допустимо простое
  ограничение по количеству без скролла как временное решение.

**B. Карточка выбранной версии (правая часть страницы, занимает оставшуюся ширину)**
- «Баннер»: прямоугольная область ~140px высотой, залитая `kBgPanel`
  (или лёгким градиентом через GDI+ `LinearGradientBrush` — необязательно,
  подойдёт и сплошная заливка), с названием версии крупным шрифтом
  (`g_fontHeading`, можно увеличить размер) поверх.
- Под баннером — две кнопки в ряд:
  - Акцентная: **«Применить эту версию»** — вызывает существующий
    `RtxRemixUpdater::downloadAndApply(destRoot, release, log, onProgress)`
    (сигнатура не меняется — он уже принимает конкретный `RtxReleaseInfo`,
    просто теперь источником будет ВЫБРАННЫЙ в списке релиз, а не
    обязательно последний).
  - Обычная: **«Открыть на GitHub»** — `ShellExecuteW(hwnd, L"open",
    release.htmlUrl.c_str(), ...)`.
- Ниже — две колонки:
  - **«Детали»**: Версия (`tagName`), Дата публикации (`publishedAt`),
    Размер архива (переиспользовать/добавить `human_size`-подобную
    функцию форматирования байт), Статус (`Установлено` /
    `Доступно к установке` — сравнение с текущей версией из
    `.rtx_remix_version.txt`).
  - **«Описание»**: текст `release.body` (это markdown с GitHub, но
    для первой версии можно выводить как обычный текст без рендеринга
    разметки) в read-only многострочном `EDIT`-контроле (как лог) с
    переносом строк.

### Acceptance criteria (когда задача считается выполненной)
1. При открытии страницы «Обновления» список из 10-20 последних
   релизов подгружается автоматически (без отдельной кнопки «Проверить»,
   хотя саму кнопку можно оставить как «Обновить список»).
2. Клик по любому релизу в списке мгновенно обновляет карточку справа
   (баннер, детали, описание) без нового сетевого запроса — данные уже
   есть в загруженном списке.
3. Кнопка «Применить эту версию» скачивает и применяет ИМЕННО выбранный
   в списке релиз — можно выбрать более старую версию, а не только
   последнюю (ключевое отличие от текущей реализации, которая работает
   только с "latest").
4. Кнопка «Открыть на GitHub» открывает страницу релиза в браузере.
5. Пункт списка, соответствующий уже применённой версии, визуально
   помечен.
6. Код по-прежнему компилируется и линкуется без ошибок под MinGW-w64
   (см. команды сборки в README.md) — это последний шаг перед тем, как
   считать задачу готовой; при работе через Antigravity агент должен

## Что это за проект

Лаунчер для Garry's Mod + RTX Remix (Metrostroi), написан на C++/Win32
без внешних зависимостей (только Windows SDK: WinHTTP, GDI+, COM/Shell,
реестр). Собирается в Visual Studio 2026.

Функции:
1. Копирование файлов игры (`bin`, `garrysmod`, `platform`, `rtx-remix`,
   `sourceengine` + несколько конфигов) из оригинальной установки Steam в
   отдельную рабочую папку — только новые/изменённые файлы при повторном
   запуске (манифест на основе размера+даты или SHA-1).
2. Проверка обновлений RTX Remix через GitHub Releases API — скачивание
   архива только при появлении новой версии, применение только реально
   изменившихся файлов (по SHA-1).
3. Проверка бета-ветки Steam (`x86-64`) для Garry's Mod через реестр +
   `appmanifest_4000.acf` (только чтение, переключение — вручную в Steam).
4. Интерфейс — тёмная тема в духе GOG Galaxy 2.0: сайдбар с навигацией
   (Обзор / Обновления RTX / Steam), скруглённые кнопки с ховер-эффектом
   через GDI+, тёмный заголовок окна (DWM immersive dark mode), консоль
   лога снизу.

## Как проверялся код

У меня (Claude) нет доступа к реальной Windows/MSVC, поэтому весь код
прогоняется через кросс-компилятор **MinGW-w64** (`x86_64-w64-mingw32-g++
-std=c++17`) на этапе разработки — это ловит синтаксические ошибки,
неверные типы, отсутствующие include'ы и т.п., но НЕ гарантирует 100%
идентичное поведение с MSVC (могут остаться специфичные для MSVC нюансы,
которые нельзя проверить без реальной сборки в VS2026). На момент последней
сессии **весь код компилируется и линкуется без единой ошибки** под MinGW.

Реальная сборка в VS2026 и визуальная/функциональная проверка на живой
Windows-машине — пользователем ещё не выполнялась (или выполнена частично,
см. секцию «Статус» ниже — обновите её после проверки).

## Известные ограничения / сознательные решения

- Обновления RTX Remix скачиваются целым zip-архивом при появлении новой
  версии (GitHub не даёт частичных/дельта-патчей готовых релизов) —
  экономия только на уровне «не скачивать, если версии совпадают» и
  «перезаписывать только изменившиеся файлы после распаковки».
- Переключение бета-ветки Steam программа НЕ делает — только проверяет и
  подсказывает, что нажать в самом Steam.
- `RtxRemixUpdater.h`: `owner = L"NVIDIAGameWorks"`, `repo = L"rtx-remix"` —
  это плейсхолдер, пользователь должен подставить точный репозиторий той
  сборки RTX Remix, которой пользуется (не может быть определено по
  скриншотам исходных файлов).
- Строки исходников — в UTF-8. Пользователю на английской Windows
  потребовалось добавить `/utf-8` в свойства проекта (C/C++ → Command
  Line → Additional Options), иначе кириллица в UI превращается в
  "кракозябры" — это уже сделано/объяснено, но стоит перепроверить при
  следующей пересборке, если появятся такие же символы.

## История уже решённых проблем (чтобы не наступать на те же грабли)

1. **LNK2019/LNK1120 (unresolved main)** — проект был настроен на
   консольную подсистему, а точка входа — `wWinMain`. Решение: Linker →
   System → SubSystem = Windows (/SUBSYSTEM:WINDOWS).
2. **C4244 wchar_t→char** в `FileSync.h::loadManifest` — конструктор
   `std::string(hashW.begin(), hashW.end())` заменён на явный цикл с
   `static_cast<char>` на каждый символ. Исправлено.
3. **Кракозябры вместо кириллицы в UI** на английской Windows — из-за
   ANSI-кодировки чтения исходников MSVC по умолчанию. Решение: флаг
   `/utf-8` в свойствах проекта (C/C++ → Command Line → Additional Options).
4. **Приватный конструктор копирования `Gdiplus::GraphicsPath`** — нельзя
   возвращать `GraphicsPath` по значению из функции. Исправлено:
   `RoundedRectPath` теперь принимает `GraphicsPath&` по ссылке и
   заполняет её на месте, а не возвращает копию.
5. **Затенение параметра `h`** в лямбде/функции `MakeLabel` (совпадали
   имена параметра-высоты и локальной переменной HWND). Исправлено
   переименованием.
6. **Кнопка «Стоп» и статус-плашка уезжали за пределы экрана** — сайдбар
   изначально создавался с произвольной высотой 2000px, и элементы,
   привязанные к «низу», считались от этих 2000px, а не от реальной
   высоты окна (720px по умолчанию) — визуально они оказывались далеко
   за пределами видимой области. Исправлено: сайдбар создаётся с реальной
   высотой клиентской области окна, а нижние элементы (`hStatusPill`,
   `hStopButton`) пересчитывают позицию в обработчике `WM_SIZE`.
7. **`GetDlgItem(hMain, ID_BTN_...)` не находил кнопки** — `GetDlgItem`
   ищет только прямых потомков окна, а кнопки лежат внутри вложенных
   панелей страниц (`hPageOverview`/`hPageUpdates`/`hPageSteam`) и
   сайдбара. Исправлено: хендлы кнопок (`hBtnSync`, `hBtnCheckRtx`,
   `hBtnDownloadRtx`, `hBtnCheckBeta`, `hStopButton`) сохраняются в
   `AppState` при создании и используются напрямую вместо `GetDlgItem`.
8. **Утечка `HBRUSH`** — кисть фона сайдбара пересоздавалась в каждом
   вызове `WM_ERASEBKGND` без удаления. Исправлено: кисть создаётся один
   раз (`g_app.brSidebar`) и удаляется в `WM_DESTROY`.
